## LLM 호출 모듈 llm.py (2026-11-13)
- 무엇을 하는가: 모든 파트의 LLM 호출을 `call_llm` 하나로 받아 role(keep·terminate·judge·analyst)별 모델로 보내고, JSON 응답을 읽어 필요한 키가 있는지 검사한다.
- 어떻게 하는가: 형식이 틀리면 오류 내용을 붙여 1회 재요청하고, API 오류는 1초·2초 대기로 최대 3회 시도한다. 호출 수(`call_llm` 횟수 + 재요청, API 재시도는 제외)가 실행당 상한을 넘으면 멈추고, 실패하면 `LLMUnavailable` 로 알려 부르는 쪽이 `확인 불가` 로 처리한다. 요청마다 시각·모델·토큰·시간을 `logs/llm_calls.jsonl` 에 남기되 프롬프트·응답 본문은 남기지 않는다. `LLM_MOCK=1` 이면 계약 샘플에서 만든 고정 응답을 쓴다.
- 한계: 실제 API 호출(`_send_real`)은 API 키를 받은 뒤 구현한다. 지금은 mock으로만 돈다. API 오류는 종류를 가리지 않고 모두 재시도한다.

## 코드 판정 decide.py (2026-11-13)
- 무엇을 하는가: 심판 점수표로 변화별 설명됨·미설명을 정하고, 미설명 개수로 `유지 / 조건부 유지 / 해지 검토` 권고와 선택지 3개의 근거를 만든다.
- 어떻게 하는가: LLM 없이 코드 규칙으로 정한다. 유지 측이 1점(`EXPLAINED_MARGIN`) 이상 앞서야 설명됨이고, 미설명 0건은 유지·2건 이하는 조건부 유지·그 이상은 해지 검토다. 미설명이 모두 13F 신호면 조건부 유지로 내린다. 근거는 양측 논거·반증 조건 문장을 그대로 옮기고 끝에 `[signal_id]`를 붙인다.
- 한계: 기준값(1점, 2건)은 기획서에 숫자가 없어 정한 기본값이라 12/5 점검에서 다시 본다. 판정은 심판 점수를 그대로 믿으므로 점수의 질은 심판 프롬프트에 달려 있다.

## 실제 LLM 호출 _send_real (2026-11-21)
- 무엇을 하는가: `LLM_MOCK=0` 일 때 모델 이름 앞부분으로 회사를 골라 실제로 보낸다. `claude-` 는 anthropic SDK, `gpt-` 는 openai SDK, `gemini-` 는 openai SDK + Gemini OpenAI 호환 주소. 응답 텍스트와 입력·출력 토큰 수를 돌려준다.
- 어떻게 하는가: 키 없음·401·403·404·거절·잘림·빈 응답은 다시 보내도 같아서 바로 `LLMUnavailable`(오류 본문은 키 일부가 섞일 수 있어 옮기지 않음). 429·5xx·60초 시간 초과(`REQUEST_TIMEOUT_SECONDS`)는 기존 재시도(최대 3회)로 넘긴다. SDK 자체 재시도는 꺼서 재시도가 겹치지 않게 했다.
- 한계: Claude(API 버전 2026-10-21)와 gpt-5 계열은 temperature 를 거부해서 보내지 않는다 → 심판 0·유지·분석 0.2 는 실제로 적용되지 않음. 실제 호출 확인(11/21): `claude-sonnet-5-5`·`gpt-5-mini` 사용 가능, 해지 측 `gemini-2.5-flash` 는 404(사용 불가), 대안 `gemini-3.8-flash` 는 503·시간 초과로 확인 못 함 → 해지 측 모델은 PM 결정 필요 (`docs/verified.md`).

## 토론 독립 작성·반박 2회 rounds.py (2026-11-23)
- 무엇을 하는가: 유지 측·해지 측이 같은 자료(밝힌 전략과 인용, 신호별 요약·설명·번호 매긴 근거, `format.py` 로 표기한 숫자, 데이터 한계)를 받아 서로의 글을 보지 않고 신호마다 논거 + 반증 조건을 쓰고, 반박 1회차(상대 논거)·2회차(상대 1회차 반박)를 한다. 정상 6번 호출.
- 어떻게 하는가: 응답마다 코드가 검사한다. 빠진 신호·신호에 없는 숫자(그 운용사 신호 전체 기준)는 문제를 모아 1회 재요청하고, 그래도 남으면 그 항목을 빼고 `warnings` 에 남긴다. 범위 밖 근거 번호는 재요청 없이 지우고 남는 번호가 없으면 논거를 뺀다. 반박 1회차에서 한쪽이라도 `concede=true` 면 `토론 불충분` 경고만 붙이고 끝까지 진행한다.
- 한계: `concede` 는 LLM이 스스로 밝히는 값이라 놓칠 수 있어 품질 점검(B6)에서 사람이 로그를 읽어야 한다. `LLMUnavailable` 은 여기서 잡지 않고 `run_debate`(심판 연결 단계)에서 처리한다. mock 응답은 고정이라 반박 1·2회차에 같은 글이 나간다.

## 심판·판정·미팅 질문과 run_debate 조립 (2026-11-23)
- 무엇을 하는가: 토론 기록을 작성자·순서를 가려(A/B 무작위, 신호 순서 섞기, 모델 이름 제외) 심판에게 점수표(10점)로 채점받고, 코드가 A/B를 되돌려 변화별 설명됨·미설명 → 권고와 선택지 3개를 정한 뒤, 미설명 변화의 반증 조건으로 미팅 질문 3개를 만든다. `run_debate` 가 토론 → 심판 → 판정 → 질문을 묶는다(정상 LLM 8번).
- 어떻게 하는가: 심판 점수·질문은 응답 검사 후 1회 재요청, 그래도 틀리면 심판은 양측 0점(미설명)·질문은 반증 조건을 그대로 쓰고 `warnings` 에 남긴다. `LLMUnavailable` 이면 `held=False`·조건부 유지·"토론을 완료하지 못함: 담당자 확인 필요". `debate_required=False` 면 LLM 없이 유지. 데모 모드는 저장본이 없어 계약 샘플 + 경고. `LLM_MOCK=1` 이면 심판 mock(A측 = 유지 측)에 맞춰 무작위 seed 를 고정해 결과가 매번 같다.
- 한계: 저장본(`debate.json`) 읽기·저장과 지문 비교는 B6에서 한다. "미설명 재료 먼저"는 프롬프트와 대체 질문 순서로만 지키고 코드로 검사하지 않는다. 문서에 없는 처리(심판 점수 실패 0점, 질문 N개, 대체 질문 경고, `check_judge` 보강, `questions_system.md`)는 PM 확인이 필요하다.
